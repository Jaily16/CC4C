## 1. 迭代背景

CC4C V3 已把原来的功能型单体升级为可验证的现代模块化单体：后端使用 Java 21、Spring Boot 3.5.16、MyBatis-Plus 3.5.17 和 Spring Modulith 1.4.12，数据库由 Flyway V1–V7 管理，安全、缓存、异步消息、可观测、Testcontainers、Docker Compose 与 GitHub Actions 均已有实现和验证证据。V3 最终门禁包含 154 项后端测试、前端依赖审计与生产构建、Trivy 源码/镜像扫描、完整 Compose 冒烟、OpenAPI 快照和持久化检查。

V4 不再以增加业务技术组件为主要目标，而是对连续迭代后形成的工程痕迹进行系统收口，让仓库从“按迭代逐步叠加的项目”转变为“结构稳定、版本一致、易读、易维护、可用两种方式部署的长期工程”。

本轮重点解决五类问题：

1. 本地仍存在 V2/V3 构建目录、扫描快照、临时 JDK、`target`、`dist`、`node_modules` 等可重建产物；仓库内也存在已经完成使命的迭代式脚本、测试和配置命名。
2. Java、Node、框架、中间件、基础镜像与 GitHub Actions 版本分散在 POM、`package.json`、Dockerfile、Compose、脚本、工作流和多份文档中，容易产生说明漂移。
3. 根目录仍使用 `back-end/CC4C`、`front-end/CC4C` 两级嵌套，性能脚本和报告带有 `aspect4`、`aspect6`、`v3` 等阶段性名称，活动文档与历史证据混在一起。
4. 仓库尚未建立统一的 EditorConfig、Java 自动格式化、前端 ESLint/Prettier 等风格门禁；部分 Java 类和 Vue 单文件组件体积过大，少量生产代码仍采用字段注入，前端仍有调试输出和不统一的文件命名。
5. Docker Compose 完整栈已经成熟，但宿主机分步骤运行仍依赖分散的 README 段落、脚本和环境变量；两种方式缺少一份共同的版本、配置、端口、启动顺序与验收契约。

## 2. V4 总体目标

V4 完成后应达到以下状态：

- 本地和仓库中的临时产物、无引用代码、废弃配置与重复说明都有明确分类；可删除项已安全清理，历史证据已归档，兼容契约得到保留。
- 全项目只有一份当前生效的技术版本基线说明，并有自动检查确保 POM、npm、Docker、Compose、Testcontainers、脚本和工作流没有版本漂移。
- 项目身份、目录、脚本、测试、性能工具和活动文档使用面向职责的稳定名称，不再以某次迭代或某个方面命名。
- 后端、前端、脚本、YAML、SQL 和 Markdown 具有统一格式；关键公共接口、事务、安全、缓存、并发、消息可靠性和部署逻辑具备准确的中文注释。
- 大文件和重复实现按职责拆分或合并，模块边界继续由 Spring Modulith 验证，前端行为和公共 API 不发生无依据变化。
- 同一份应用能够通过“完整 Docker Compose”与“宿主机分步骤模块化部署”两种方式运行，两种方式共享环境变量、秘密边界、数据库迁移、端口和健康检查语义。
- README 只承担项目介绍和快速入口；详细版本、开发、部署、运维与历史证据进入各自唯一文档，链接可验证且不会互相复制大段内容。

## 3. 不属于本次迭代

- 不新增课程、博客、评论、收藏、审核或账号业务功能。
- 不把六模块单体拆成微服务，也不引入 Spring Cloud、Nacos、Seata、Kubernetes 或服务网格。
- 不因“看起来更新”而盲目升级版本；只有兼容性、安全修复或统一基线需要时才成组升级。
- 不改变现有 URL、DTO、`code/data/msg`、HTTP 状态、分页、Long ID 字符串、Cookie、CSRF、OpenAPI 和前端路由契约，除非某方面的独立计划证明必须调整并同步测试。
- 不重写 Flyway V1–V7，不重命名已经发布的消息事件 `*.v1`，不伪造数据库 down migration。
- 不把注释数量当质量指标，不为显而易见的 getter、循环或赋值添加逐行注释。
- 不内置默认管理员、密码、Token、SMTP 授权码或任何真实秘密。

## 4. 全局实施原则

### 4.1 清理分类先于删除

所有候选项必须先进入清单，再分为三类：

| 类别 | 处理原则 | 典型内容 |
| --- | --- | --- |
| 可重建垃圾 | 精确验证路径后删除，并记录重新生成命令 | `temp/`、`target/`、`dist/`、`node_modules/`、扫描快照、临时工具副本、运行日志 |
| 历史证据 | 移入历史归档或保留原位，不参与当前配置 | V1–V3 规划、迭代记录、脱敏性能与故障报告、历史 SQL |
| 运行/兼容资产 | 禁止当作垃圾删除 | 本机秘密、Compose 卷、数据库备份、上传文件、Flyway 迁移、消息事件版本、OpenAPI 契约 |

不得使用 `git clean`、`git reset --hard`、`git checkout --`、`stash`、`down -v`、`FLUSHDB`、`FLUSHALL`、Flyway `clean/repair` 或按进程名批量终止服务完成清理。

### 4.2 版本说明唯一、机器声明可校验

V4 将建立一份当前技术版本基线作为唯一人工说明来源。POM、`package.json`、锁文件、Dockerfile 和 Actions 仍需保留各自工具要求的机器声明，但不得再由 README、运行手册和多个报告分别维护相互独立的版本表。自动脚本必须验证这些机器声明与版本基线一致。

### 4.3 先移动、后改内容

目录规范化必须先以 `git mv` 完成可识别的纯移动，再调整包名、导入、脚本路径和内容；大规模格式化与注释补充必须放在移动之后。每个逻辑检查点独立验证，避免一个提交同时混合删除、移动、格式化和行为重构。

### 4.4 注释解释“为什么”

中文注释主要覆盖：

- 模块公开接口、类型化配置、公共 DTO 和受控异常的用途与约束；
- 事务边界、所有权校验、CSRF、密码、限流和秘密处理的安全原因；
- Cache-Aside、generation 失效、单飞、短锁与故障旁路语义；
- Outbox/Inbox、Publisher Confirm、ACK、重试、DLQ、租约和幂等边界；
- 指标低基数、请求关联、健康分组与脱敏要求；
- 部署脚本的前置条件、破坏性边界、失败恢复和退出码。

标识符、API 字段、日志键、SQL、协议名和标准技术术语保持英文，避免为了中文化破坏生态兼容。注释必须与测试和实现同步，过时注释视为缺陷。

### 4.5 保持安全网连续

每个方面都必须从 `8f29872` 的已通过基线出发，并在进入下一方面前完成相称的自动验证。结构和风格变化不得降低 154 项后端测试、前端安全测试、Flyway、Modulith、OpenAPI、Compose、Trivy 和浏览器验收覆盖。

### 方面一：基线盘点与安全清理

**目标：** 在不破坏数据、秘密、历史证据和公共契约的前提下，清除本地可重建垃圾及仓库内可证明无用的遗留。

范围包括：

- 统计 `temp/` 中 V2/V3 构建、Trivy 快照、临时 JDK/工具副本以及 `target/dist/node_modules/logs` 的大小、来源和重建方式。
- 检查 Git 跟踪、忽略、未跟踪和本地秘密边界，形成精确“删除/保留/归档”清单。
- 使用引用扫描、编译、测试和运行入口证明死代码、废弃脚本、无效配置、重复资源或旧兼容层是否仍被使用。
- 删除动作优先采用回收站或可恢复隔离目录；任何递归删除前都必须校验解析后的绝对路径位于当前工作区内。
- 清理后重建必要依赖与产物，证明仓库仍可从干净状态完成测试和构建。

本方面不进行目录大搬迁、版本升级、全仓格式化或双部署改造。`LegacyCookieCleanupFilter`、Flyway `V1–V7`、`*.v1` 消息事件、历史报告和数据库 `legacy` 文件不能仅凭名称判定删除。

**完成门禁：** 有可审阅的清理清单和删除依据；秘密、卷、数据库、上传文件与历史证据未受影响；工作区只剩明确需要的忽略文件；完整质量基线无回退。

### 方面二：版本、依赖与项目身份统一

**目标：** 建立唯一版本基线和一致项目身份，消除跨 POM、npm、Docker、Compose、脚本、工作流与文档的版本漂移。

范围包括：

- 建立 `versions.yml`（最终文件名由方面二计划锁定）及版本一致性校验脚本；README 只链接该清单，不再复制完整版本表。
- 按运行环境分组验证兼容性：Java/Spring/MyBatis；Node/Vue/Vite；MySQL/Flyway/Connector；Redis/Lettuce/Session；RabbitMQ/Spring AMQP；Prometheus/Grafana；Testcontainers/容器镜像。
- 使用 Maven BOM、`dependencyManagement`、Maven Enforcer 和 npm lockfile 收敛依赖；审查 AMQP Client、Netty 等安全覆盖，只有存在明确修复依据时才保留。
- 统一 Maven `groupId/artifactId/name/version`、npm `name/version/packageManager/engines`、Spring application name、镜像名和脚本显示名称，消除 `com.CC4C`、`myvue`、`0.0.0` 等不一致身份。
- Docker 标签继续固定 digest，GitHub Actions 继续固定完整提交 SHA；自动检查版本目录与机器声明的一致性。

不要求为了 V4 统一提升所有组件版本；如需升级，必须按兼容组一次完成并通过完整测试。Flyway 迁移版本、消息 schema 版本和 Git 标签属于不同概念，不得合并为项目版本。

**完成门禁：** 唯一版本清单可被机器验证；Maven 依赖收敛、npm 审计和 Docker/Actions 固定检查通过；各环境显示相同项目身份；README 与运行手册没有独立维护的冲突版本表。

### 方面三：仓库与源码结构规范化

**目标：** 将目录、脚本、测试和文档改为面向职责的长期结构，消除明显的迭代式外观，同时保留 Git 历史和兼容资产。

范围包括：

- 将 `back-end/CC4C`、`front-end/CC4C` 收敛为稳定的 `backend`、`frontend` 入口，并同步 Maven、npm、Docker、Compose、Actions、脚本、OpenAPI、截图和文档路径。
- 将数据库、RabbitMQ、观测、部署和通用脚本按基础设施/开发/测试/性能/部署职责归位。
- 把 `run-aspect4-benchmark`、`run-aspect6-gatling`、`Aspect2ContractFunctionalTest`、`Aspect4BenchmarkApplication` 等活动名称改为业务或用途名称；性能输出不再写入 `v3/aspectN` 目录。
- 活动架构、开发、运维、参考文档与 V1–V3 历史规划/报告分离；历史材料保留事实，不作为当前配置来源。
- 后端继续保持 `shared/identity/catalog/community/interaction/moderation` 六模块；跨模块只通过具名 API。前端按页面领域、共享组件、组合式函数、API 和状态职责整理。
- 对重复包装、重复常量、重复错误处理和相邻职责进行合并；对过大的缓存、可靠消息、领域服务和 Vue 页面按单一职责拆分。拆分/合并必须以行为测试为依据，不能只按文件行数机械处理。

Compose 项目名、卷名、Redis namespace 和 RabbitMQ namespace 带有 `v3` 时不能直接改名：项目名变化会影响卷发现，namespace 变化可能导致会话失效、缓存冷启动或消息队列并存。方面三必须给出兼容迁移、积压排空与回滚方案。

**完成门禁：** 根目录和活动源码不再出现无业务含义的 `aspectN`/`v3` 命名；所有路径引用、模块验证、OpenAPI、镜像构建和两类前端路由均正常；历史迁移和事件兼容不变。

### 方面四：代码风格、中文注释与内部整合

**目标：** 建立自动执行的代码规范，在最终目录上统一格式、命名和注释，并降低大类、大组件与重复逻辑的维护成本。

范围包括：

- 根目录增加 `.editorconfig`，统一 UTF-8、LF、末尾换行、缩进和空白规则。
- 后端使用与 Java 21 兼容的自动格式化和静态检查；生产 Bean 使用构造器注入与 `private final`，允许测试基类在有明确理由时使用框架注入。
- 前端引入与 Node 24/Vue 3/Vite 8 兼容的 ESLint Flat Config、Prettier，并按需要增加 Stylelint；移除调试 `console.log`、修复 `header.vue`、`sliber.vue` 等命名。
- 为模块 API、类型化配置、事务、安全、缓存、消息、观测和危险脚本补充准确中文说明；公开 Java 类型使用中文 Javadoc，复杂 Vue 状态与组合逻辑说明数据流和边界。
- 评审超大文件和重复模式：优先抽取稳定职责与可测试函数，不进行无证据的全量 Options API→Composition API、Java record 化或 Lombok 清除。
- 将格式化、静态检查、注释/编码检查接入本地脚本与 GitHub Actions；生成代码、锁文件、Flyway SQL 和历史证据采用适合各自格式的规则。

**完成门禁：** 全仓格式化和静态检查通过；生产代码不存在无理由字段注入、遗留调试输出和乱码；中文注释覆盖关键约束但不堆砌显而易见说明；功能、性能和安全契约无变化。

### 方面五：容器与宿主机双运行模式

**目标：** 用同一套配置契约提供两种受支持的部署方式，而不是维护两个分叉版本。

#### 模式 A：Docker Compose 完整部署

- 保留根目录一条稳定命令启动前端、后端、MySQL、两个 Redis、RabbitMQ、Mailpit、Prometheus 和 Grafana。
- 保留非 root、只读根、Compose secrets、内部数据库/Redis/AMQP 网络、持久卷、健康检查、管理员引导、外部 SMTP 覆盖和安全重置。
- 解决项目名/卷名从 `cc4c-v3` 迁移到中性名称时的数据发现问题，普通升级不得删除现有卷。

#### 模式 B：宿主机分步骤模块化部署

- 提供清晰顺序：MySQL/Flyway → 安全 Redis → 业务缓存 Redis → RabbitMQ → Mailpit 或外部 SMTP → 后端 JAR → 前端开发服务或静态 Nginx → 可选 Prometheus/Grafana。
- 每个组件都有独立前置检查、脱敏配置模板、启动/停止/健康检查和失败恢复说明；脚本只管理自己精确启动的 PID 或服务。
- 后端仍是一个模块化单体 JAR。“分模块部署”指前端、后端、数据库、中间件和观测组件可分步骤部署，不把六个 Spring Modulith 业务模块拆成六个进程。
- 两种模式共享环境变量名称、端口、Cookie/CSRF、Flyway、上传目录、Rabbit topology、观测端点和秘密要求；配置一致性由自动测试验证。

**完成门禁：** 两种模式均可从干净环境启动并完成相同核心业务冒烟；数据库和上传数据在正常重启后持久；容器模式和宿主机模式之间的配置差异只有主机名、路径和秘密注入方式。

### 方面六：全量验证、文档收口与发布准备

**目标：** 证明 V4 只改善工程质量而未破坏 V3 能力，并把当前文档从“迭代记录集合”收敛为可长期维护的项目入口。

范围包括：

- 后端完整 Testcontainers、六模块、Flyway V1–V7、Security、Cache、Outbox/Rabbit、Actuator、OpenAPI 与性能回归。
- 前端单元/组件安全测试、lint、格式化、npm audit、生产构建和关键路由浏览器回归。
- 两种部署模式的空环境、已有数据、重启持久化、上传、邮件、管理员引导、观测和故障恢复验收。
- GitHub Actions 增加版本一致性、风格、目录、死链接和双运行模式门禁；Trivy、Dependency Review、Compose/OpenAPI/Prometheus/Grafana 检查继续保留。
- README 精简为项目介绍、架构摘要、快速开始和文档导航；当前版本、开发规范、部署运维各保留一份权威文档；V1–V3 材料进入只读历史区。

```text

  ↓ 形成可信净基线

  ↓ 锁定后续所有工具和名称

方面五 双运行模式
  ↓ 使用最终路径、版本和配置契约
```

不得为了并行而跨方面提前实施。尤其不能在方面一清理时顺便搬目录，不能在方面二版本统一时顺便格式化全仓，也不能在方面三改路径时同时重写业务逻辑。

## 9. 主要兼容性风险

| 风险 | 可能后果 | V4 控制方式 |
| --- | --- | --- |
| 递归删除目标解析错误 | 删除秘密、数据或工作区外文件 | 删除前解析绝对路径、限定工作区、精确清单、优先可恢复操作 |
| 把“V1/V2/V3”一律当遗留 | 破坏 Flyway、消息兼容或历史证据 | 区分迁移/协议版本、历史文档和活动迭代命名 |
| 后端/前端目录改名 | Docker、Actions、脚本、截图和文档路径失效 | 先全仓引用图，再 `git mv`，逐入口验证 |
| Maven/npm 项目身份调整 | JAR 名、镜像 COPY、缓存和发布坐标变化 | 明确旧→新映射，保留兼容入口或一次性迁移脚本 |
| Compose 项目名/卷名调整 | 看似“数据丢失”，实际挂载到新空卷 | 固定显式卷名或执行校验过的数据迁移，禁止 `down -v` |
| Redis/Rabbit namespace 调整 | Session 失效、缓存冷启动、消息积压遗留 | 安全 namespace 保持或计划重登录；消息先排空/双读后切换 |
| 一次性格式化与重构混合 | Git blame 丢失、评审困难、行为缺陷难定位 | 移动、格式化、重构分提交，格式化提交不改变行为 |
| 过度注释或翻译标识符 | 注释过时、生态工具不兼容 | 中文解释设计理由，标准技术标识与协议字段保持英文 |
| 两套部署配置独立维护 | 环境变量、端口与安全语义漂移 | 共享配置清单与自动一致性测试，只允许注入方式不同 |
| 手工模式读取旧配置 | 本机秘密泄露或加载错误配置 | 只使用忽略的 env/secret 文件，显式指定脱敏配置名 |

## 10. 验证与安全规则

- 规划与实施期间不得读取、修改、复制、暂存或打包 `backend/src/main/resources/application.yml`（目录调整前对应当前 `back-end/CC4C/src/main/resources/application.yml`）。
- 不读取或输出 `.env.*.local`、`deploy/secrets/local`、数据库备份、Cookie、Token、SMTP 授权码、Pepper、AES 密钥或连接凭据。
- 本地垃圾清理不得影响 Docker 卷、MySQL 数据、Redis 持久化、RabbitMQ 队列、上传目录或 Git 历史证据。
- 所有递归删除、移动和服务停止必须先精确识别目标；禁止使用宽泛通配符和按进程名批量操作。
- 每个方面开始前确认 `HEAD`、工作区和基线提交；结束前执行 `git diff --check`、敏感信息扫描和预期文件清单审查。
- 每个方面独立本地提交，但只有用户明确授权后才能暂存和提交；推送、打标签和发布镜像需要再次独立授权。
- 回滚只能逆向恢复当前方面涉及的文件或切换到已记录镜像/备份，不使用破坏性 Git、Flyway 或消息队列清理命令。
